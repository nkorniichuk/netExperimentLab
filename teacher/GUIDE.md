# Посібник викладача

## Підготовка пари

1. На комп’ютері аудиторії перевірте Docker Engine командою `docker version`. Виконайте повну збірку з мережі та контрольні прогони нижче. Підтвердьте, що `tc` може встановити `netem` у контейнері з `NET_ADMIN`. Для Docker Desktop це залежить від Linux-ядра його VM.
2. Видайте студентам лише каталог `student/`.

Студенти складають команду `docker build`, дописують команду компіляції CMake та `COPY` у `Dockerfile`, а в `run.sh` пишуть створення мережі та запуск двох контейнерів. Готові команди є в `reference/Dockerfile`, `reference/run.sh` і нижче. На одну пару достатньо одного запуску в кожному режимі. Повтор корисний для порівняння розкиду за наявності часу.

## Контрольний прогін

З каталогу `teacher/reference/` виконайте:

```bash
docker build -t srt-lab:1.5.4 .
docker run --rm srt-lab:1.5.4 srt-file-transmit -version
mkdir -p input
dd if=/dev/urandom of=input/payload.bin bs=1048576 count=8
bash run.sh baseline
bash run.sh delay
bash run.sh loss
```

Успішний прогін друкує два однакових SHA‑256, повідомлення `OK: SHA-256 matches` та рядок із часом і швидкістю. Кожна спроба створює новий каталог під `runs/`. Стан черги зберігається в `metrics/netem.txt` для двох режимів із `netem`. Порівняйте час, RTT, відкинуті пакети й повторні передачі. Значення з CSV залежать від версії CLI та моменту останнього знімка. Для коротких запусків або діагностики відсутність CSV не заважає перевірити основний результат через SHA‑256 і `tc`.

`run.sh` викликає `verify.sh` після завершення приймача і зберігає його вивід у `hashes.txt`. Приймайте також вивід окремого запуску скрипта з двома шляхами: спочатку до оригіналу, потім до отриманого файлу. За різних хешів або помилки читання скрипт завершується з ненульовим кодом.

## Еталон Compose

Після підготовки образу та вхідного файлу виконайте з каталогу `teacher/reference/`:

```bash
(
  set -e
  mkdir -p runs
  SRT_COMPOSE_RUN=$(mktemp -d "$PWD/runs/compose.XXXXXX")
  export SRT_COMPOSE_RUN
  export COMPOSE_PROJECT_NAME="srt-lab-compose-$(basename "$SRT_COMPOSE_RUN" | tr '[:upper:].' '[:lower:]-')"
  mkdir "$SRT_COMPOSE_RUN/output" "$SRT_COMPOSE_RUN/metrics"
  trap 'docker compose down' EXIT
  docker compose up -d --wait --wait-timeout 15 receiver
  docker compose run --rm sender
  docker compose wait receiver
  bash verify.sh input/payload.bin "$SRT_COMPOSE_RUN/output/payload.bin"
  cat "$SRT_COMPOSE_RUN/metrics/result.csv"
)
```

Compose використовує той самий образ і той самий скрипт вимірювання. Готовність приймача визначає перевірка UDP-сокета. Бонусний сценарій використовує базовий режим і завершується перевіркою SHA‑256.

## Приклад оформлення результату

| Режим | Спроба | Секунди | Мбіт/с | SHA‑256 збігається | tc dropped | Повторні передачі SRT |
|---|---:|---:|---:|---|---:|---:|
| baseline | 1 | 0,50 | 134,218 | так | — | — |
| delay 40 ms | 1 | 1,00 | 67,109 | так | 0 | — |
| loss 1% | 1 | 0,80 | 83,886 | так | 57 | — |

**Приклад висновку.** У цьому прикладі режим із затримкою мав найбільший виміряний час. За втрати пакетів `tc` відкинув 57 пакетів, але отриманий файл мав той самий SHA‑256. Це узгоджується з надійною доставкою SRT. Точне число повторних передач потрібне зі статистики SRT. Один запуск у кожному режимі дає лише попереднє порівняння.

## Орієнтири для усного розбору

- Ім’я `receiver` розпізнається в спільній bridge-мережі. `localhost` у відправнику належить його власному мережевому простору. Публікація порту була б потрібна для звернення через порт хоста.
- `netem` діє на виході відправника. Пакети у зворотному напрямку не проходять через цю чергу. Встановлення SRT-з’єднання входить у виміряний час, тому короткі передачі особливо чутливі до затримки та накладних витрат.
- Лічильники `tc` і SRT спостерігають різні події. Наприклад, qdisc бачить усі пакети на інтерфейсі, а SRT вимірює повтори своїх пакетів. Важливо пояснити фактичні результати, навіть якщо порядок швидкостей різниться між спробами.
