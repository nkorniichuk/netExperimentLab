# Передача файлу через SRT у Docker

**Мета.** Зібрати SRT CLI з вихідного коду, передати файл між контейнерами й виміряти, як контрольовані затримка та втрати змінюють передачу.

**Потрібно.** Docker Engine із Linux-контейнерами, Bash, доступ до GitHub і реєстру образів під час першої збірки. Працюйте з каталогу `student/`. На Windows використовуйте Bash у WSL 2 з увімкненою інтеграцією Docker. Для експерименту Linux-ядро середовища Docker має підтримувати `netem`.

## 1. Збери образ

1. Переконайся, що `docker version` показує секції `Client` і `Server`.
2. У першій стадії `Dockerfile` уже є завантаження Haivision SRT `v1.5.4` і конфігурація CMake. Заміни `false` на команду компіляції. Використай режим `cmake --build`, каталог збірки `/build` і ціль `srt-file-transmit` (підказка `--target`). Наступний рядок перемістить бінарник у `/srt-file-transmit`.
3. У другій стадії допиши `COPY --from=...`, щоб бінарник опинився в `/usr/local/bin/`.
4. Самостійно склади команду `docker build`. Контекстом збірки має бути поточний каталог, а тегом образу — `srt-lab:1.5.4` (підказка `-t`). Поки триває збірка, прочитай [конспект](NOTES.md) та виконай крок 2. Після збірки перевір версію програми.

```bash
docker run --rm srt-lab:1.5.4 srt-file-transmit -version
```

## 2. Підготуй дані й розрахунок

Створи один файл 8 MiB. Цей самий файл використовуй у всіх режимах.

```bash
mkdir -p input
dd if=/dev/urandom of=input/payload.bin bs=1048576 count=8
wc -c < input/payload.bin
```

Результат має бути `8388608` байтів. У `measure.sh` знайди блок `awk`. Заміни вихід із кодом 2 у цьому блоці на `printf`, що обчислює та друкує середню швидкість корисних даних у Мбіт/с із трьома десятковими знаками. Формула є в конспекті. Збережи перевірку, що час більший за нуль.

## 3. Передай файл без штучних погіршень

**Напиши три команди Docker у `run.sh`.** Заміни блоки-заглушки біля відповідних `TODO`. Скрипт уже створює каталоги, чекає на готовність приймача, збирає логи й прибирає контейнери та мережу. Для синтаксису команд можна використати `docker network create --help` і `docker run --help`.

1. **Створи мережу.** Дай їй ім’я зі змінної `"$network"`, вибери драйвер `bridge` і зроби мережу внутрішньою (підказки `--driver`, `--internal`).
2. **Запусти приймач.** Використай образ `"$image"`, ім’я контейнера `"$receiver"` і мережу `"$network"`. Запусти його у фоні (`-d`) і додай мережевий псевдонім `receiver` (`--network-alias`). Змонтуй `"$run/output"` із хоста в `/output` для запису (`--mount`). Після образу передай команду для слухача:

   ```bash
   timeout -k 3s 90s srt-file-transmit 'srt://:9000?mode=listener' 'file:///output'
   ```

3. **Запусти відправник.** Використай той самий образ і мережу, ім’я `"$sender"` та `--rm`. Перед назвою образу додай розгортання масиву `capability`, наведене в коментарі до `TODO`. Воно дасть відправнику право налаштовувати `netem` у наступному кроці. Після образу передай `bash /measure.sh "$scenario" receiver`.

   | Шлях на хості | Шлях у відправнику | Доступ |
   |---|---|---|
   | `$PWD/input` | `/input` | лише читання |
   | `$PWD/measure.sh` | `/measure.sh` | лише читання |
   | `$run/metrics` | `/metrics` | читання й запис |

   Для кожного монтування передай окремий параметр `--mount` зі значенням у формі `"type=bind,src=ШЛЯХ_ХОСТА,dst=ШЛЯХ_КОНТЕЙНЕРА"`. Для доступу лише на читання додай `,readonly` усередині лапок.

Запусти базову передачу своїми командами через скрипт:

```bash
bash run.sh baseline
```

Приймач слухає UDP-порт 9000. Перед відправленням `run.sh` перевіряє його сокет через `ss`. Відправник звертається до приймача за псевдонімом `receiver`.

**Перевір цілісність файлу.** Готовий `verify.sh` приймає два шляхи на хості в порядку **оригінал, отриманий файл**. Він обчислює і друкує SHA‑256 обох файлів, показує `OK: SHA-256 matches` за збігу та завершується з ненульовим кодом, якщо хеші різні або файл не вдалося прочитати. `run.sh` автоматично викликає його після завершення приймача й записує результат у `hashes.txt`.

Один раз запусти перевірку окремо. Заміни `runs/baseline.ABC123` фактичним шляхом із рядка `Run files`.

```bash
bash verify.sh input/payload.bin runs/baseline.ABC123/output/payload.bin
```

У каталозі запуску також відкрий `sender.log`, `receiver.log` і `metrics/result.csv`. Якщо перевірка цілісності не пройшла, познач спробу як невдалу.

## 4. Зміни умови мережі

У `measure.sh` у гілках `delay` та `loss` заміни тимчасовий вихід із кодом 2 на виклики `tc`. Загальна форма команди:

```bash
tc qdisc replace dev eth0 root netem limit 10000 <параметри>
```

Використай окремо `delay 40ms` та `loss random 1%`. Кожна спроба запускає свіжий контейнер, тому налаштування попереднього запуску не успадковуються. `NET_ADMIN` надається відправнику тільки у двох режимах із `netem`.

```bash
bash run.sh delay
bash run.sh loss
```

У `metrics/netem.txt` знайди застосоване правило і лічильник `dropped`. У `metrics/srt.csv` за наявності знайди RTT та накопичувальний лічильник повторних передач відправника. Вкажи точні назви колонок, які використав. Якщо CSV порожній або поле відсутнє, запиши «немає даних» і зроби висновок за часом, SHA‑256 та лічильниками `tc`.

Для звіту достатньо однієї успішної спроби в кожному режимі. Якщо залишився час, повтори всі три режими й порівняй розкид. Залиш невдалі спроби в таблиці й поясни, що побачив у логах.

## 5. Здай результат

- Змінені `Dockerfile`, `run.sh` і `measure.sh` та команда `docker build` у звіті.
- Заповнений [шаблон звіту](REPORT.md) та логи або CSV, з яких узято цифри.
- Короткі відповіді на запитання в шаблоні.

## Бонус. Повтори базову передачу через Compose

Опиши в `compose.yaml` два сервіси `receiver` і `sender` зі спільним образом і окремими директоріями для вхідних даних та результатів. Використай команди та монтування з `run.sh` як підказку. Створи порожню вихідну папку для цього запуску, запусти приймач, дочекайся відкриття UDP-сокета, тоді запусти відправника. Дочекайся завершення приймача й перевір SHA‑256. Відправник має звертатися до імені сервісу `receiver`. Заверши командою `docker compose down`.

## Якщо запуск не вдався

| Симптом | Що перевірити |
|---|---|
| `Cannot connect` або `permission denied` до сокета Docker | Чи працює Docker Engine і чи доступний він поточному користувачеві. |
| Помилка копіювання або `not found` під час збірки | Шлях до бінарника в стадії `build` і шлях призначення. |
| `Receiver did not bind UDP port 9000` | Лог приймача, URI `srt://:9000?mode=listener`, монтування вихідної папки. |
| `Operation not permitted` від `tc` або невідомий `netem` | Перший випадок вказує на права контейнера або політику Docker. У другому перевір підтримку `netem` у Linux-ядрі середовища Docker. |
| Таймаут, немає файлу або SHA‑256 різні | Збережи логи обох контейнерів. Перевір режим і повтори спробу з новим вихідним каталогом. |
